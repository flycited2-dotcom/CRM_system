# CRM Stage 0-1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first runnable CRM foundation: monorepo, local infrastructure config, backend authorization/RBAC/work-session/audit core, and a minimal role-aware frontend shell.

**Architecture:** The project is a TypeScript monorepo with `apps/api` for NestJS and `apps/web` for Next.js. PostgreSQL is accessed through Prisma, Redis is reserved for queues/session-adjacent background work, and all security decisions happen in the backend. The frontend is intentionally thin: it logs in, stores tokens, calls API endpoints, and renders role-aware admin/user screens.

**Tech Stack:** Node.js, npm workspaces, NestJS, Next.js App Router, TypeScript, Prisma, PostgreSQL, Redis, JWT, bcryptjs, Swagger/OpenAPI, React Hook Form, Zod.

---

## Scope

This plan covers only Stage 0 and Stage 1 from the project documentation:

- repository and monorepo setup;
- backend application shell;
- frontend application shell;
- PostgreSQL/Redis Docker Compose config;
- Prisma schema and seed data;
- roles, permissions, users;
- login, logout, refresh token rotation;
- work sessions;
- audit log;
- basic user administration API;
- minimal frontend login and users page.

Excluded from this slice: clients, leads, deals, tasks, commercial offers, Telegram, email, site webhooks, tenders, 1C integration, production deployment.

## Success Criteria

- `npm.cmd install` completes at the root.
- `npm.cmd run prisma:generate -w apps/api` generates Prisma Client.
- `npm.cmd run build -w apps/api` succeeds.
- `npm.cmd run build -w apps/web` succeeds.
- Backend exposes Swagger at `/api/docs`.
- Seed creates roles `owner`, `manager_head`, `manager`, `accountant`, `admin`.
- Seed creates an active owner user from env defaults.
- Login returns access token, refresh token, and current user profile.
- Login creates a `work_sessions` row and `activity_logs` login row.
- Logout closes the active work session, revokes the refresh token, and writes audit.
- RBAC protects user administration endpoints.
- Frontend login page reaches the API and routes an authenticated user to the dashboard.

- [ ] **Step 1: Write auth service behavior**

`AuthService.login()` validates credentials, rejects blocked users, creates a work session, writes a `user.login` audit event, and returns tokens plus user profile.

- [ ] **Step 2: Write refresh behavior**

`AuthService.refresh()` validates an active refresh token, revokes it, creates a replacement, and returns a new token pair.

- [ ] **Step 3: Write logout behavior**

`AuthService.logout()` revokes the supplied refresh token, closes the latest open work session for the user, updates `lastLogoutAt`, and writes `user.logout`.

- [ ] **Step 4: Protect endpoints**

JWT guard parses `Authorization: Bearer <token>`. Permission guard checks backend permissions, not frontend role labels.
